Systems & tools

A cheque that had not been cashed could be marked as paid because another cheque in the same run was a few dollars away
The cash projection clears an expected payment when it finds a bank line of about the same amount on about the same day, allowing a margin of half a percent. Payroll cheques written in the same run are routinely closer together than that. Cheque #3854 for $1,053.23 was cleared against cheque #3860 for $1,057.93 — $4.70 apart against a $5.27 margin — while #3854 was still uncashed. The money leaves the account either way, so the projected closing figure never moved and nothing looked wrong; what disappeared was the record that the payment was still outstanding, which is exactly the kind of error that survives a spot check. The projection now refuses to clear anything carrying a cheque number unless the bank line carries that same number, which the system already required elsewhere and simply was not applying here.
Yesterday's report reached the site only after a stalled build was restarted, so a published file is now checked on the page rather than on the push
The report is put live by sending the file to the hosting service, which then rebuilds the site. Yesterday's rebuild started and never finished, so the file was on the server and the page still could not be opened. Restarting the build cleared it in 22 seconds, against the 21 hours it had been stuck. The lesson is that sending a file is not the same as publishing it, so the check that now runs after every report is not whether the file was sent but whether the page itself serves the right content — verified this time by fetching the live page and counting the figures in it, not by trusting a success message.
